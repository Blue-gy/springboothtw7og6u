## 1. 项目概述

### 1.1 项目背景

当前高校校园内的场地预约（如会议室、体育场馆、教室等）和设备租赁普遍依赖**人工登记、微信群沟通或纸质表格**进行管理。这种传统方式存在以下痛点：

- **效率低下**：学生需要多次往返管理处确认场地档期
- **信息不透明**：无法实时查看场地占用状态，易产生时间冲突
- **流程断裂**：从预约、审批、使用、归还到财务结算缺乏统一管理
- **数据缺失**：管理员无法统计分析场地使用率和财务状况

本系统旨在为高校提供一个**一体化的在线预约管理平台**，打通场地预约、设备租赁、课程管理、活动报名、财务管理等全流程。

### 1.2 产品定位

面向高校的**轻量级、全流程**校园资源预约管理 SaaS 产品。以场地和设备的预约管理为核心，向外拓展课程管理、活动报名、比赛管理等辅助功能，最终实现校园资源管理的全面线上化。

### 1.3 目标用户

| 用户角色 | 描述 | 核心诉求 |
|---------|------|---------|
| **学生/会员** | 在校学生，系统主要使用者 | 快速预约场地、查看档期、报修申请 |
| **员工/审核者** | 各场馆或部门管理人员 | 审核预约申请、处理维修工单、管理租赁归还 |
| **系统管理员** | 校级管理角色，拥有最高权限 | 数据统计、系统配置、用户管理、全局调度 |

### 1.4 产品范围

- **包含**：场地管理、设备租赁、课程预约、活动报名、比赛管理、维修工单、财务管理、用户权限系统
- **不包含**：支付系统对接（V1.0 仅记录财务数据，不实现在线支付）、移动端 App（V1.0 为 Web 响应式）

## 2. 市场分析与用户研究

### 2.1 竞品分析摘要

| 竞品维度 | 传统人工管理 | 通用预约系统 | 本产品差异 |
|---------|------------|------------|-----------|
| 场地预约 | 纸质/微信 | 单一功能 | **多维度资源联动**（场地+设备+课程） |
| 设备管理 | 无系统 | 独立系统 | **与场地预约打通**，一站管理 |
| 财务统计 | 手工记账 | 无/简单 | **自动生成消费统计和报表** |
| 用户权限 | 无 | 简单 RBAC | **三级角色 + 细粒度按钮权限** |

### 2.2 用户痛点优先级

1. **P0 - 场地时间冲突**：学生预约后发现时间已被占用
2. **P0 - 审批流程不明**：不知道预约是否通过，需要反复确认
3. **P1 - 财务对账困难**：管理员月底对账需要逐条核对
4. **P1 - 维修报修拖延**：设备损坏后缺乏标准报修和跟进流程
5. **P2 - 活动信息分散**：课程、比赛、活动信息零散，缺乏统一入口

## 3. 产品目标与成功指标

### 3.1 核心目标

| 目标 | 衡量方式 |
|------|---------|
| 场地预约效率提升 | 预约完成时间从平均 30 分钟降至 3 分钟 |
| 减少预约冲突 | 场地时间冲突率降低至 0 |
| 管理透明化 | 所有预约、租赁记录可追溯、可查询 |
| 数据驱动决策 | 管理员可通过统计图表了解使用率和财务状况 |

### 3.2 关键结果（OKR）

- 管理员可在一页内查看所有场地当前状态
- 用户端预约全流程不超过 3 步操作
- 系统支持同时管理 15+ 场地、6+ 设备类型
- 财务模块覆盖会员消费、场地租赁费用、设备租赁费用三个维度

## 4. 用户画像与使用场景

### 4.1 用户画像

#### 👤 小李 — 学生用户
> "我想预约篮球场，但不知道明天下午有没有空位"

- 年龄：20 岁，大二学生
- 使用频率：每周 1-2 次
- 场景：预约场地、报名活动、查看课程、设备报修
- 痛点：看不到实时档期，经常跑空

#### 👤 王老师 — 场地管理员
> "每天要处理几十条预约，还要协调冲突"

- 年龄：35 岁，场馆管理员
- 使用频率：每天
- 场景：审核预约申请、处理维修工单、管理设备归还
- 痛点：预约量大、冲突频繁、手工统计费时

#### 👤 赵主任 — 系统管理员
> "我想知道这个月哪些场地最受欢迎，收支情况如何"

- 年龄：45 岁，后勤主任
- 使用频率：每周
- 场景：查看统计报表、管理用户权限、系统配置
- 痛点：缺乏数据支持决策

### 4.2 核心使用场景

| 场景编号 | 场景名称 | 用户角色 | 操作步骤 |
|---------|---------|---------|---------|
| S01 | 场地预约 | 学生 | 浏览场地 → 选择时间段 → 提交预约 → 等待审核 |
| S02 | 预约审核 | 管理员 | 查看待审核列表 → 确认/拒绝 → 预约状态更新 |
| S03 | 设备租赁 | 学生 | 浏览设备 → 选择数量/时间 → 提交租赁 → 支付登记 |
| S04 | 维修报修 | 学生 | 提交报修 → 描述故障 → 管理员派单 → 维修记录 |
| S05 | 财务统计 | 管理员 | 选择时间范围 → 查看收入/支出图表 → 导出报表 |

## 6. 非功能需求

| 需求类别 | 需求描述 |
|---------|---------|
| **性能** | 页面加载时间 < 3 秒；支持 50+ 并发用户 |
| **可用性** | 界面简洁，用户无需培训即可完成核心操作 |
| **安全性** | Shiro 框架实现认证授权；密码加密存储；防止 SQL 注入 |
| **兼容性** | 支持 Chrome / Firefox / Edge 等主流浏览器 |
| **可维护性** | 前后端分离架构，便于独立升级和部署 |
| **数据一致性** | 场地预约时间冲突在后端数据层严格校验 |

## 8. 业务流程图

### 8.1 核心流程：场地预约

> **[ 图 1：场地预约泳道图 ]**
> 
> 请在此处插入场地预约泳道图（参考文件：`puml/01_用例图_管理员.puml` 至 `puml/20_活动图_场地预约（带泳道）.puml`）
> 
> **流程描述：**
> 1. 用户浏览场地列表，选择目标场地
> 2. 进入场地详情页，查看可用时间段
> 3. 选择日期和时间段，填写预约说明，提交申请
> 4. 系统后端校验时间冲突（数据库层面查询已有预约）
> 5. 管理员在后台"场地预约管理"中查看待审核列表
> 6. 管理员审核通过/拒绝，填写审核意见
> 7. 用户端预约状态更新，可查看审核结果

### 8.2 核心流程：设备租赁与归还

> **[ 图 2：设备租赁归还流程图 ]**
>
> **流程描述：**
> 1. 用户浏览设备列表，加入"购物车"
> 2. 提交租赁申请，填写数量和租赁时长
> 3. 生成订单（状态：未支付）
> 4. 管理员确认收款后，订单状态变更为"已支付"
> 5. 设备出库（状态：已发货）
> 6. 用户使用完毕后，管理员确认归还
> 7. 设备库存恢复，订单状态变更为"已完成"

### 8.3 核心流程：维修工单

> **[ 图 3：维修工单泳道图 ]**
> 
> **流程描述：**
> 1. 用户发现场地/设备故障，提交维修申请
> 2. 管理员查看工单，确认并派单
> 3. 维修人员进行维修
> 4. 维修完成后录入维修记录
> 5. 用户确认修复结果

| bisai | 比赛信息 | 比赛名称、类型、时间、赛制 |
| orders | 订单表 | 订单号、金额、状态（6 种状态流转） |
| caiwuqingkuang | 财务情况 | 用户ID、消费金额、消费类型、日期 |
| token | 认证令牌 | 用户ID、token、过期时间 |
| config | 系统配置 | 轮播图、公告、全局参数 |

> 完整数据库共 **36 张表**，覆盖用户权限、业务管理、财务管理、系统配置四大领域。

### 10.2 关键数据校验规则

| 规则 | 实现方式 |
|------|---------|
| 场地时间不可重叠 | 数据库查询已有预约的时间区间，提交时校验冲突 |
| 设备库存不可为负 | 租赁时检查库存，归还时自动+1 |
| 用户权限隔离 | Shiro 注解 + 拦截器，不同角色看到不同菜单 |
| 订单状态流转 | 未支付 → 已支付 → 已发货 → 已完成 / 已取消 → 已退款 |
